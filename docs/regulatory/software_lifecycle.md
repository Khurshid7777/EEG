# Жизненный цикл ПО (IEC 62304) — черновик

## 1. Класс безопасности ПО

Предлагаемый класс — **B**: травма возможна, но не серьёзная, при учёте внешних мер — обязательного
просмотра врачом. Довод за **C**: функция тревог о приступах в ОРИТ при отсутствии иной защиты.
Решение — после утверждения назначения монитора (`regulatory_pathway.md` §1). До этого процессы
ведутся с запасом, по требованиям класса C, где это не дорого.

## 2. Архитектура и разделение на элементы

Шесть слоёв (`src/neurolens/layer1_ingest` … `layer6_interpret`), связанных контрактами
(`contracts/`); мониторинг реального времени (`realtime/`); API (`api/`). Сегрегация, важная для
безопасности:
* критические находки (`critical/safety.py`) формируются независимо от текстового слоя;
* текстовый слой не может добавить находку без ссылки (валидатор заземления).

* Изменение модели или порога по умолчанию:
  1. пре-регистрация гипотез и правил решения (`docs/preregistration_increment*.md`, коммит до

  Отрицательный результат фиксируется и не внедряется (например, инкременты 40, 43, 44, 45).
* Решения и их обоснования — `DECISIONS.md` (D1–D83).

## 4. Верификация

* Автотесты: 35+ модулей в `tests/`, около 300 тестов. Охват — чтение всех форматов (в том числе
  сверка с эталонными реализациями), предобработка, детекторы, правила, API, монитор, LSL. Запуск —
  `pytest`. Перед каждым коммитом изменений в коде — полный прогон.
* Сверка читателей форматов с независимыми реализациями: MNE-Python (Nihon Kohden, Persyst), neo
  (Micromed).
* Системная проверка — пре-регистрированные прогоны конвейера целиком на внешних наборах
  (`clinical_evaluation.md`).

**Не хватает для СМК:**
* план верификации по выпуску;
* протоколы с подписью;
* матрица «требование → тест» в формате СМК (черновая прослеживаемость — §6).

## 7. Сопровождение и проблемы

Отклонения от ожидаемого поведения на внешних данных оформляются как решения (D-номер) с
контекстом, решением и последствиями; примеры — D69 (модель отменяла вспышку-подавление), D76–D78.
Обратная связь врачей собирается через `/feedback`; калибровка уверенности — по исправлениям
(`calibration/`). Для пост-маркетингового наблюдения нужен регламент сбора и разбора исправлений.
